# Behind-the-meter solar: lightweight NZ grid estimate

Status: **lightweight research prototype**, 23 October 2026.  Script added as `build_embedded_solar_quicklook.py`, but no live run or regression validation has been completed.

## Aim

Show a **good general idea** of how much embedded/distributed solar is already generating in New Zealand, alongside dispatched utility-scale solar.  Prefer transparency, low cost and a smooth daily profile to precision.  Do not label the resulting values as metered generation.

Keep three measures separate:

- **Embedded PV gross generation**: electricity generated by non-dispatched home, business and other embedded arrays, including energy exported to a distribution network.
- **Self-consumed PV**: energy generated and consumed directly on site, unseen by ordinary grid-demand readings.
- **Exported PV**: output injected back into the network, some of which is visible in EA reconciliation/export data.  Do not add this a second time when deriving underlying demand.

The existing repository already includes `estimate_btm_solar_2024.py`, `model/btm_solar_assumptions.json`, and up-to-date EA installation data under `data/distributed_generation/`.  These remain separate from any new near-live quick-look estimate.

## Public benchmark (September 2026)

- This repository's EA DG summary records **1,278.336 MW** registered all-solar capacity and **507.801 MW** in its residential-solar category as of 2026-09-30.  Do not treat all registered solar as hidden BTM: dispatched solar farms appear in the register too.
- [Elenz's embedded-solar method](https://elenz.co.nz/methods/embedded-solar) removes approximately **410 MW** of separately dispatched solar farms from about **1,270 MW** of total installed capacity, leaving approximately **860 MW** of embedded capacity (about **574 MW** North Island, **287 MW** South Island, subject to rounding).  Its model includes some commercial and ground-mounted arrays not included in residential-only classifications.
- Elenz reports **about 95 GWh** of modelled *gross* embedded PV in September 2026; **46.6 GWh** was metered as local-network solar exports.  The implied approximately **48.4 GWh** consumed on-site is an inference, not a direct meter observation.  Gross average for the month was **~132 MW** (95,000 MWh / 720 h), or **~3.17 GWh/day**.
- These numbers are a useful independent plausibility check, not a licence to represent Elenz's estimates as EA-measured output or substitute them uncredited as original work.

## First-pass live model: optional implementation

Use freely accessible [Open-Meteo satellite radiation](https://open-meteo.com/en/docs/satellite-radiation-api) from Himawari (10-minute native observations, archived from 2023, approximately 30-minute availability delay).  Query a small handful of representative NI/SI sites and use regional capacity weights.  This provides cloud-sensitive power estimates without waiting for scarce historical ground stations.

A deliberately simple indicative equation for each area:

```
embedded_ac_mw[t, region] ~= installed_embedded_ac_mw[region]
                           * clamp(satellite_GHI_w_m2[t, region] / 1000, 0, 1)
                           * approximate_roof_and_system_factor
```

Use 0.7–0.85 as *illustrative sensitivity cases only*, not experimentally fitted derating rates.  GHI is horizontal irradiance while roofs are tilted and have mixed directions, so this quick proxy is not a physical PV model.  Actual geometry, panel temperature, DC/AC ratio, shading and weather add uncertainty.  Take averages across several representative locations rather than using a single clear/cloudy station to stand for an island.

Important: the sun's elevation and day length are *already represented in GHI*.  Avoid layering an unverified daily/monthly seasonal multiplier that counts seasonal change twice.  If empirical corrections become available, fit them smoothly over day-of-year, with a documented calibration sample.

For the dashboard, label as `Estimated embedded solar`, distinguish from dispatched solar, display source/time of most recent irradiance, and include a deliberately broad uncertainty annotation.  Do not add estimated embedded PV into a generation total without also clearly indicating corresponding adjustments to the demand accounting: a grid-balance chart must not accidentally double count exported PV.

## Weather Underground station investigation

Manual evidence supplied by project maintainer:
- [IWHANG385 (Whangārei)](https://www.wunderground.com/dashboard/pws/IWHANG385): a 22 October 2026 table includes 5-minute temperature, UV and numerical `Solar` (W/m²) observations.  This **confirms at least one station reports usable *relative* irradiance variation**.  Large apparent peaks are a reason to normalise and quality-check before treating values as absolute irradiance.

Additional page candidates located:
- [IWHANGAR47, RDS Maungatapere](https://www.wunderground.com/dashboard/pws/IWHANGAR47): station metadata / radiation field present; the retrieved page showed offline and *no verifiable radiation rows*.
- [IWHANGAR43, Whangārei Heads](https://www.wunderground.com/dashboard/pws/IWHANGAR43): page exists but showed offline / no historical rows for the page checked.

**Do not count field labels in an empty Weather Underground table as proof of an installed radiation sensor or usable historical archive.**  Neither the number of reliably active Northland solar stations nor earliest available solar dates could be established from the accessible public pages.

[Weather Underground PWS historical API](https://developer.weather.com/docs/openapi/pws-historical-2-0) supports `hourly`, `daily` and native-interval `all` observations by station ID and date, but requires an API key.  The site's [PWS Data Feed terms](https://wx-next-privacy.vercel.weather.com/privacy/terms-of-use) prohibit derivative works from Feed data and restrict use to personal non-commercial purposes.  Do **not** commit a scraper, automate collection from WU, or redistribute a historical WU-derived dataset without confirming rights.  Prefer independently licensed data from station owners themselves when available.

Local station readings should therefore be a **later verification layer**, not a production dependency.  Their strongest role is checking whether Himawari-derived cloud fluctuations track real local changes, using authorised observations.

## Minimal next implementation steps

1. **Show the benchmark now**: roughly 860 MW installed embedded solar and ~95 GWh estimated for September 2026, with attributed source and approximate / dated labels.
2. **Trial the quick-look script** with `python build_embedded_solar_quicklook.py --date 2026-10-21`.  It requests eight representative NI/SI Himawari satellite points and emits date-stamped native 10-minute embedded-MW proxy plus daily MWh, with explicit data-coverage flag.  It is a prototype and has not yet been verified against live responses or added to an automated workflow.  Replace the initial equal-within-island spatial averages with installed-capacity weighting when convenient.
3. **Validate order of magnitude** against Elenz monthly gross output and EA solar exports, remembering exports omit on-site use.
4. **Optionally test local PWS trends** using owner-authorised data later, only if that would meaningfully improve a dashboard intended for general understanding.

This does not require a NIWA DataHub subscription, a Weather Underground API key, a 25 kW subcategory reconstruction, or paired-day GXP regression.
